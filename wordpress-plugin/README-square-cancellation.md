# Standard解約申請・利用終了管理

Square Dashboardでの解約操作は管理者が行います。WordPressは申請・終了日・通知を管理し、Square API解約、Webhook、自動プラン変更、猶予期間は実装しません。

## 利用者と管理者の操作

1. Standardユーザーはマイページの`[egov_plan_status]`から「Standardを解約する」を押します。既存の独立申込ページ`[egov_standard_application]`で確認画面を表示し、「確定して解約を申請する」を押した場合のみ保存します。JavaScriptは不要です。
2. ログイン中のユーザーと最新の`standard_approved`履歴から承認対象契約を特定します。複数契約の先頭を推測で選択しません。履歴・契約・プランが一致しない場合や契約なしのテスト用Standardユーザーは申請できず、管理者確認を案内します。
3. 申請日時を保存し、申請・監査を同じトランザクションで確定します。プランはStandardのままです。管理者メールが失敗しても申請は保持します。フォームnonce、署名付き状態、ユーザー行ロック、承認履歴IDのUNIQUE制約で不正・二重申請を防止します。
4. 管理者は通知メールのリンクから対象ユーザーのSquare契約管理を開きます。終了日なしは「未処理」と表示します。Square Dashboardでキャンセル操作と終了日を確認し、確認チェック・理由・終了日を保存します。後日の修正も可能で、古いフォームは拒否します。**日付やチェックはSquareの解約を技術的に証明するものではありません。**
5. マイページへ「契約状況：解約予定」と利用終了日を表示します。利用者にも`wp_mail()`で終了日を通知します。利用終了日はWordPressのタイムゾーンで当日23:59までとし、当日いっぱいStandardを利用できる案内です。
6. WordPressのタイムゾーンで終了日の翌日から、Standardのままであれば管理者へ期限通知します。終了日当日は期限通知しません。管理者が既存の「Standard承認を解除」でFreeへ変更すると、解約申請完了・完了監査も同じトランザクションで保存し、以降の通知を停止します。ウォッチ上限処理・AI回数の保持・確定後キャッシュ処理は既存のままです。

申請済みはボタンを隠し「解約申請を受け付けました。手続き完了後に利用終了日をお知らせします。」と表示します。期限到来後も管理者の解除まではプランを自動変更しません。Freeから再承認した場合は新しい承認履歴IDで別申請を作成でき、過去の申請は保持します。

## 保存先とスキーマ

既存の契約・監査・ユーザーメタのスキーマは変更せず、`{prefix}egov_square_cancellations`を追加します。既存データを削除・初期化しません。

| カラム | 用途 |
|---|---|
| `id` | 自動採番の主キー |
| `user_id`, `contract_id`, `approval_id` | 対象ユーザー・契約・Standard承認履歴。`approval_id`はUNIQUE、`user_id`は検索用INDEX |
| `requested_at`, `updated_at`, `completed_at` | 申請・更新・完了日時。UTC保存、画面ではサイト時刻へ変換 |
| `end_date` | Squareで管理者が確認した利用終了日。サイトの暦日、DATE・NULL可 |
| `revision` | 日付変更・完了の競合検出。通知の更新では変更しない |
| `admin_notified_at`, `user_notified_revision` | 申請通知の受付日時、利用者へ終了日通知済みの版 |
| `last_mail_attempt_at` | 送信再試行のクールダウン |
| `last_due_attempt_date`, `last_due_sent_date` | サイト暦日での期限通知試行日・送信処理受付日 |
| `mail_claim_token`, `mail_claimed_at` | 同時メール処理を防ぐ予約。画面・監査には表示しない |

新規有効化と既存サイトの`admin_init`で`dbDelta()`を実行できます。実メタデータで必須カラム・主キー・UNIQUE・インデックス・InnoDBを確認できた場合だけ`egov_law_monitor_cancellation_schema_version = 1`を保存します。保存処理も実メタデータを確認し、同一DB・InnoDBを保証できなければ拒否します。独立した既存mysqli接続を再利用します。

既存のFree解除へは、解約申請がある場合の完了処理だけを追加しています。新テーブルがまだ存在しない既存サイトでは従来の解除が可能です。テーブルが存在するのに不完全・読取失敗の場合は、整合性を守るため解除トランザクションも取り消します。管理者がスキーマを修復してから再操作してください。COMMIT応答喪失やROLLBACK失敗は結果不明として、再操作前の状態確認を案内します。

監査は既存テーブルの次の操作名を使用します：`subscription_cancellation_requested`、`subscription_end_date_set`、`subscription_end_date_changed`、`subscription_cancellation_completed`。利用者申請は`admin_user_id=0`とJSON内の利用者ID、管理操作は管理者ID、Cronで既にFreeであることを確認した完了はシステムとして区別します。

## メールとWP-Cron

- WordPress標準の`wp_mail()`を使用し、サイトのSMTPプラグイン等をそのまま利用します。管理者宛先は`admin_email`です。専用SMTP認証設定は追加しません。`wp_mail()`のtrueは送信処理受付であり、受信箱への到達保証ではありません。[WordPress公式](https://developer.wordpress.org/reference/functions/wp_mail/)
- 申請通知・利用者への終了日通知は保存後に送信を試み、失敗時は約1時間のクールダウン後にCronで再試行します。通知予約・メール送信・結果保存を分離し、SMTP中にDBトランザクションを保持しません。日付編集直後などは先の送信から1時間後の通知になる場合があります。
- 期限通知は**失敗・応答不明を含め、送信試行を1サイト暦日1回まで**に制限します。送信前に試行日を確定するため、結果保存失敗やクラッシュでも同日の重複送信を避けます。失敗時の期限再通知は翌日です。通常の申請通知・終了日通知とは別の制限です。
- 通知予約は15分、全送信の再試行クールダウンは1時間です。SMTP成功直後にプロセス停止して結果保存できなかった場合、申請・終了日通知は再送される可能性があります。外部メール配送との完全なexactly-onceは保証しません。期限通知は上記の保守的な日次上限を優先します。
- `egov_standard_cancellation_cron`を`hourly`で登録します。最大100件×10ページ・約20秒の処理枠と継続カーソルで分割し、翌実行に引き継ぎます。重複実行時もユーザー行ロック・通知予約・日付で重複を防ぎます。
- WP-Cronはアクセス時に実行されるため、厳密な時刻は保証しません。`DISABLE_WP_CRON`利用時やアクセスの少ないサイトは、既存のサーバーCronからWordPress Cronを起動してください。[WordPress公式](https://developer.wordpress.org/reference/functions/wp_schedule_event/)
- Freeへの変更と送信前の再確認で以後の通知を止めますが、既にSMTP処理に入ったメールは取り消せません。プラグイン外からメタを直接変更した場合はCronがFreeを検出して申請完了を記録します。承認履歴が異なる場合は通知・編集を停止し、管理者確認を案内します。

## 反映・検証

コードの一式反映後、管理者が管理画面へアクセスして新テーブルとスキーマバージョンを確認してください。既存テーブルの削除・初期化や手動のALTERは不要です。新PHPの不足、古いOPcache、キャッシュされた個人向けページに注意します。

1. ステージングのテストユーザーを請求書経由でStandard承認し、契約と承認履歴が対応することを確認。
2. マイページから確認画面へ進み、戻る操作で申請されないこと、確定で申請・監査・管理者メールが記録されることを確認。
3. 実在のSquare契約をテストで解約せず、確認済みのテスト情報で終了日登録・修正、利用者表示と通知、古いフォーム拒否を確認。
4. テスト用日付で当日の期限通知なし・翌日からの期限通知、日次重複防止、手動承認解除後のFree・完了監査・通知停止を確認。
5. メール配送、WP-Cron／外部Cron、永続オブジェクトキャッシュ、実DB同時実行・障害時の挙動は実環境で別途検証。

ローカルは`php tests/square-cancellation-test.php`と既存Square回帰テストを実行します。実DB・Square API・メール配送はモック化します。ロールバック時も新テーブル・申請履歴は削除しないでください。旧コードへ戻す場合は残ったCronイベントを管理者が停止する必要があります。
