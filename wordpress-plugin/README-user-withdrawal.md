# 管理者用・退会管理

「法令ウォッチ → ユーザー管理」の各ユーザーの「退会管理」から開きます。マイページまたは問い合わせ窓口で受け付けた退会申請を、同じ画面で一段階ずつ手動処理します。次の操作は自動実行しません。

## マイページからの退会申請

Free・Standardの一般会員は「ご利用プラン」タブ下部の「退会を申請する」から確認画面を開き、チェックして確定します。確認画面を開くだけでは保存しません。ログイン・ユーザー別nonce・ログインIDと対象IDの一致・既存の会員保護判定をサーバー側で検証します。管理者・サービス用等の保護対象は申請対象外です。

受付はWordPress Options APIで`egov_law_monitor_withdrawal_request_{ユーザーID}`へ保存し、autoloadは無効です。Freeの新規受付は`user_id`、UTCのISO 8601日時`requested_at`、`status=received`の3項目です。Standard連携は`approval_id`・`contract_id`・`cancellation_id`・`cancellation_attempt`を加えた7項目とし、`status`は`pending_cancellation`（連携未完了）または`received`（連携確認済み）です。最初の受付日時は再照合時も維持します。旧3項目optionはそのまま読み取れ、Standardの旧記録は明示操作でのみ連携します。GETでの移行・解約申請作成は行いません。

Standardは現在の承認・契約と、確認画面の退会nonce・既存解約nonce・契約トークンを検証し、optionの途中記録を保存してから既存の解約申請関数を呼びます。承認IDと契約IDが一致する既存申請は重複登録せず利用し、終了日は上書きしません。現在の契約・承認が変わった場合は古いフォームや別の承認サイクルへの付け替えを拒否します。Freeの過去の解約履歴は連携対象として選び直さず、変更しません。

`cancellation_attempt`は`ready`（未試行）、`uncertain`（試行開始済み・結果未確定）、`failed`（確定した失敗）、`confirmed`（対応行確認済み）です。呼出前にuncertainを永続保存し、途中終了・COMMIT結果不明・後続読み取り失敗を自動再試行しません。uncertainで対応する申請が見つからない場合は管理者調査へ案内します。対応行が確認できる場合、または確定失敗から再試行する場合に限り、ユーザーの明示POSTで再照合します。optionの最終更新だけが失敗した場合も既存の解約申請を再利用します。option保存前の失敗では解約処理を呼ばず、途中記録を削除して巻き戻す処理もありません。

成功時は303で元のページ・タブへ戻します。失敗や未完了は確認画面・管理画面で明示し、両方の受付完了と表示しません。JavaScriptは不要です。解約受付メールは既存の送信予約・失敗時再試行を再利用し、配送失敗によって受付済みの両記録は取り消しません。

申請受付は既存の`egov_user_withdrawals`へ書き込まず、8段階の退会処理を開始しません。ウォッチ・AI要約・プラン等の通常機能は変更しません。解約保存には既存の独立接続・ユーザー行ロック・トランザクションをそのまま使い、新しい横断トランザクションや通常処理の追加ロック・自動再試行は導入しません。管理者が別途退会処理を開始した後の保存制限は従来どおりです。

Standard解約だけの場合はアカウントをFreeとして継続利用します。Standardユーザーのアカウント退会申請にはStandard解約申請を含め、別々の申請は不要です。Freeはアカウント退会のみです。いずれもSquareでの実際の解約・課金停止は管理者が手動で行い、利用終了日も従来どおり管理者が登録します。申請だけではプラン変更・アカウントや個人履歴の削除は行いません。支払済み期間はStandardを維持し、終了後のFree変更・8段階の退会処理も手動です。

管理画面の手順1に受付状態・ユーザーID・申請日時（サイトのタイムゾーン）と、連携対象の承認ID・契約ID・解約申請IDを表示します。pending_cancellationや参照不明は連携未完了として表示し、退会開始も拒否します。手動でFreeへ変えただけではpendingは解消しません。既存のSquare確認・Free・利用終了日等の条件も維持します。本人確認チェックは自動選択せず、問い合わせ窓口による申請も従来どおり受け付けます。

既存の退会監査は受付optionの申請日時等を保存していないため、退会完了時にもoptionを削除しません。氏名・メール・理由等は複製せず、ユーザー削除後も同じ退会管理画面で受付記録を参照できます。保持期間の運用は別途定めてください。退会申請取消・退会専用の申請メール・退会監査への受付情報追加は今回の対象外です。

`php tests/user-withdrawal-request-test.php`と`php tests/withdrawal-cancellation-integration-test.php`で受付・連携・重複・部分失敗・結果不明・明示再照合・開始条件をオフライン検証します。実WordPressのOptions API・永続キャッシュ・並行POST、実MySQLのCOMMIT/接続断、UsersWPの実際のタブURLは本番反映前にステージングで確認してください。optionと解約テーブルの同時確定は保証せず、途中状態を保持して確認する方式です。

## 対象と事前確認

- 操作者は`manage_options`が必要です。WordPressユーザー削除・削除再準備・削除後再清掃には`delete_users`も必要です。
- 対象はSubscriberのみです。他ロール併有、管理・投稿・内部API権限、管理者本人、`law_watch_api`、明示的な保護対象ID、マルチサイトは対象外です。
- サービス用IDは「設定 → e-Gov Law Monitor AI」の保護対象設定で追加します。設定不正時も対象判定を停止します。Application Password登録だけでは恒久的に除外せず、用途確認の警告を出します。
- Free・Standardの両方でSquare Dashboardの契約・課金停止・支払済み期間の終了を管理者が確認します。必要なSquare解約と正式なFree変更は既存の管理機能で事前に手動実施してください。
- 画面のWordPress保存情報や確認チェックは、Square側の実際の契約終了を証明しません。退会処理からSquare APIは呼びません。

## 8手順と開始条件

| 手順 | 管理者の操作・主な条件 |
| --- | --- |
| 1. 退会申請・本人確認 | 申請受付・本人確認を明示的にチェックします。 |
| 2. Square契約終了・課金停止・利用終了日の確認 | 契約確認・必要な解約完了・支払済み期間終了等をチェックし、Subscription ID・確認日時・終了日等の根拠を記入します。不要な個人情報は記入しません。 |
| 3. 退会前チェック | ユーザー・保存プラン・Square契約・解約申請・旧申込・ウォッチ・AI履歴・同意・所有投稿/メディア/コメント/リンクを確認します。読み取り失敗は記録なしや0件に置き換えません。旧申込テーブル不存在は区別します。 |
| 4. 退会処理開始 | 存在する対象会員、未開始、Free、必要な管理者確認と根拠、未完了解約なし、旧申込はclosed、既存解約履歴は完了済みかつ終了日の翌日以降であること等を再検証します。契約のCustomer/Subscription ID不足・読み取り失敗は拒否します。所有コンテンツは開始時に残っていても構いません。開始取消機能はありません。 |
| 5. 法令ウォッチの削除 | `started`のみ。件数と対象範囲を確認し、有効・停止中を含む全ウォッチと通知設定を削除します。残存0件と監査を記録します。 |
| 6. AI要約の個人履歴削除 | `started`で、同じUUIDの手順5監査とウォッチ・通知設定の残存0件が必要です。個人履歴とFree試用回数を削除し、残存0件と監査を記録します。 |
| 7. WordPressユーザー削除 | `started`、同じUUIDの手順5・6監査、個人データ残存0件、Free、Square関連の未解決事項なし、必要な同意・保持記録が必要です。所有投稿・メディア・本人コメント・所有リンクがある場合は先に整理してください。最終確認後に標準`wp_delete_user($user_id, null)`を一度だけ呼びます。 |
| 8. 残存データ確認・退会完了 | `deleting`で、ユーザー不存在、全削除対象の残存0件、必要な開始・清掃・削除開始・正常終了監査と契約・解約・同意保持を確認します。明示的な最終確認後にのみ完了を記録します。追加削除は行いません。 |

契約・解約・旧申込の確認は各100件未満を対象とし、上限到達時は確認完了と扱わず停止します。未完了申請や各件数は全件集計します。契約履歴がないFree会員でも、Square確認は省略しません。

## 削除するデータと保持する記録

| 区分 | 対象 |
| --- | --- |
| 手順5で削除 | `{prefix}law_watch_settings`の対象user_id全行、usermetaの`egov_law_monitor_notifications`全行 |
| 手順6で削除 | `{prefix}egov_law_ai_summary_history`の対象user_id全行、usermetaの`egov_law_monitor_ai_summary_trial_usage`全行 |
| 手順7で削除 | WordPress標準処理による対象ユーザーと全user_meta。所有コンテンツは事前整理が必須で、他ユーザーへの移管や削除をこの処理で行いません。 |
| 保持 | Square契約・解約履歴・旧申込履歴、退会監査と退会状態、必要なStandard同意の監査内保持記録 |
| 対象外・維持 | 全ユーザー共通のAI要約キャッシュ`{prefix}egov_law_ai_summaries`、他ユーザーのデータ |

Standardの月間回数は個人履歴から集計し、別の月間回数メタはありません。Standard同意`egov_law_monitor_standard_consent`は標準削除でメタ自体が消えるため、手順7の削除前監査へ`agreed_at`・`terms_version`・旧`conditions_version`（存在時）を保持します。契約・承認履歴があるのに必要な同意がない場合は削除を拒否します。元々同意が不要なFree会員に推測値を作りません。

## 状態・監査・保持記録の検証

既存の`{prefix}egov_user_withdrawals`（InnoDB）を利用します。主キー`process_uuid`、UNIQUEな`user_id`、`phase`、`revision`、`claim_token/claimed_at`、`started_audit_id/last_audit_id`、作成・更新・完了日時（UTC）で管理します。この画面のための追加テーブル・カラムはありません。

レコードなしが未開始、手順4〜6は`started`、手順7〜8の完了前は`deleting`、最終完了は`completed`です。旧`cleaned`状態を個別清掃完了と推測せず、未知・不正・読取不能な状態でも停止します。claimはユーザー削除段階用で、通常保存の予約ではありません。

- 開始監査に、契約・解約・旧申込のID別検証ハッシュと同意の有無・ハッシュを保存します。削除前と完了前に共通検証し、同件数でもID差替え・欠落・必要監査の欠落を拒否します。
- 同じIDの正当な契約訂正は既存の`subscription_updated`・`standard_approved`監査、終了日訂正・解約完了は対応する既存監査の連続した変更前後で検証します。対象ユーザー・管理者・ID・許可項目・監査順序を確認し、終了日訂正はDashboard確認とrevision増分も必要です。
- 変更監査なし・追跡不能・未対応項目・レコード追加/ID置換・旧申込/同意の未対応変更は拒否します。変更監査は200件までとし、超過や検証manifestのない旧開始監査は推測で補完しません。
- 清掃・残存確認・監査・revision更新は既存の独立mysqli接続で同一トランザクションにします。users行→退会状態行のロック順を維持し、対象テーブルのInnoDBを要求します。失敗・競合は成功にしません。
- WordPress標準削除は独自トランザクションの外で実行します。削除前の`deleting`と監査、標準削除、削除後の結果監査を分け、後段失敗を「WordPress削除をロールバックした」とは扱いません。
- 完了監査`withdrawal_completed`と`deleting → completed`、completed_at・revision・最新監査IDは同時に確定します。COMMIT応答不明は再読込して状態・監査を確認し、成功や取消を断定しません。

## 削除後の画面と復旧

ユーザー削除後も`admin.php?page=egov-user-withdrawal-check&user_id=対象ID`を開きます。退会処理レコードと監査を使い、同じ画面で契約・同意・監査、残存件数、手順8を確認できます。「残存データを再確認」はGETによる読取りのみです。

| 状態 | 対応 |
| --- | --- |
| 削除未実行 | 標準削除呼出前の停止は監査の呼出有無で区別します。停止理由と元の処理を調査します。自動再実行しません。 |
| 明確なfalse終了・ユーザー存在 | 同じUUIDの失敗監査、元の削除前条件と保持情報の一致を確認できる場合だけ「削除失敗を確認して再準備」を表示します。監査付きでstartedへ戻すだけで、削除は別操作です。 |
| 正常終了・結果監査まで確定 | 最新の残存・保持情報を確認し、問題がなければ手順8を別途実行します。 |
| 正常終了後の結果監査保存失敗、例外・中断・結果不明 | 永続的な成功証拠がない場合は復旧不能として停止します。ユーザー不存在や管理者の申告から成功監査を作成しません。元の処理・ログ・削除フックの手動調査が必要です。 |

削除後にウォッチ・通知設定・AI個人履歴・Free試用回数が残った場合は、`deleting`、同一UUIDの正常終了監査、必要な先行監査・契約・同意保持を検証できる場合のみ「削除後の残存データを再清掃」を表示します。ユーザー/所有コンテンツ/対象外メタの残存や読取失敗は停止します。

再清掃は対象4種類に限定し、清掃前後件数・元の削除成功監査ID・直前監査IDを`withdrawal_residuals_cleaned`へ記録し、清掃とrevision更新を一括確定します。再清掃監査の連鎖も確認し、100段階超過では調査を求めます。再清掃後は残存を再確認し、完了を別途操作してください。遅延書込み再発時も最新情報で明示的に再清掃できます。時間経過だけのclaim解除・強制完了はありません。

## POST再送信対策と操作結果

全7種類の変更操作（開始、ウォッチ削除、AI削除、ユーザー削除、削除再準備、再清掃、完了）は、管理画面の`load-$page_hook`でHTML出力前に処理します。権限・nonce・対象・UUID/revision/署名・保持条件は各既存操作が再検証します。結果は303で同じ対象IDの退会管理GETへ戻します。表示関数はPOSTを実行しません。

操作結果はWordPress transientに5分間保存し、管理者ID・ログインセッション・対象IDとランダムな参照IDに結び付けます。URLに結果本文・個人情報・契約情報・nonceは載せず、GETの成功/失敗パラメータも信用しません。結果は一度表示すると消費し、期限切れ・読取不能・保存失敗では成功表示せず、最新状態と監査の確認を案内します。一時結果は監査の代用ではありません。

通常のリダイレクト後の再読み込みはGETです。古いフォームを戻る操作で再送信した場合も、既存の状態・署名・revision等による二重実行防止を維持します。PRGはnonceを一回限りにする仕組みではなく、通信断・プロセス中断等の結果不明時は再実行せず調査してください。権限不足・不正な対象IDなど、安全な対象画面を特定できない要求は拒否します。

## 通常機能への影響と限界

通常のウォッチ・通知設定・AI履歴・Free試用回数・Standard同意はWordPress標準APIで保存し、保存直前に退会状態を読みます。処理開始済み・完了済み・読取失敗では保存を拒否します。保存予約（writing）や通常保存用独立接続・追加トランザクションは使用しません。外部通信後にも保存前に再確認します。

確認直後に退会が始まり、開始前の保存が後から完了する競合は残ります。遅延書込みや外部プラグインの直接保存まで排除せず、削除後の残存確認で対応します。Free履歴保存と回数更新の部分成功リスク・自動補正なしの仕様は維持します。

Squareの契約登録・Standard承認・新規解約申請等は処理中に拒否します。退会に必要な既存の管理者Free変更と終了日の登録/訂正は、従来の検証を維持したまま処理中も利用できます。完了済み・不正状態・読取失敗は拒否します。必要なメール通知は開始前に済ませてください。

清掃のメタ削除はトランザクション内の対象キー限定SQLで行い、metadata削除フックは実行しません。確定後・結果不明時はユーザーメタキャッシュを無効化します。通常保存の標準フックは維持します。標準削除の権限フィルターは、直接wp_delete_user()・直接SQL・外部プラグインの独自経路まで阻止するものではありません。

## テストと本番反映前の確認

`tests/user-withdrawal-*-test.php`は実際の業務関数・PRG処理を通し、DB・WordPress境界のみ代替します。8手順、保持記録の故障注入、失敗/不明時の停止、再清掃、303とGET結果表示/再読込を検証します。PHP全テスト・構文チェック、通知UIのJavaScriptテスト、git diff --checkも実行します。

実WordPress・MySQLのロック/接続断/COMMIT、UsersWP等の削除フック・独自データ、永続キャッシュ、管理画面の実ブラウザでのリダイレクト・戻る操作は未検証です。他プラグインの削除副作用は本処理で取り消せません。導入前にステージングで全手順と保持履歴を確認し、DB・アップロード等をバックアップしてください。コードの差し戻しだけでは削除データを復元できません。履歴保持期間・個人情報の運用方針は別途定めてください。
