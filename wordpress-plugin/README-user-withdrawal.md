# 管理者用・退会前チェック

「法令ウォッチ → ユーザー管理」の各一般会員の「退会前チェック」から開きます。管理者本人、管理権限・投稿権限・内部API権限を持つ対象、subscriber以外のロールは対象外です。既存コードのAPIユーザー名`law_watch_api`も除外します。Application Passwordの登録がある場合はサービス用途の確認を求める警告を表示します。登録だけを理由に一般会員を恒久的に除外しません。認証情報そのものは表示しません。

GitHub Secretsに保存される投稿用・内部API用ユーザー名を、この画面から確認することはできません。既知の条件だけでサービスアカウントを完全に識別できるとは限らないため、管理者が別途確認してください。

画面はユーザー情報、保存プラン、Square契約、解約申請、旧申込、ウォッチ件数・通知設定、AI個人履歴件数・お試し回数、Standard同意記録、所有投稿タイプ別件数・コメント・リンク件数をSELECTで取得します。契約・解約・旧申込の詳細表示は最新100件、未完了解約と各件数は全件集計です。共有AIキャッシュは対象外です。

旧申込テーブルの不存在と読み取りエラーを区別します。その他の必要情報の取得に失敗した場合も、0件に置き換えません。プラン上限の適用など書込みを伴う既存取得関数は呼びません。

WordPressに保存した情報だけの確認であり、本人確認・Square Dashboardでの契約終了と課金停止の確認は別途必要です。「確認対象記録なし」でも退会可能とは判定しません。この段階には削除・承認解除・同意退避・監査書込み・Square API通信はありません。

投稿・メディアはWordPressの投稿タイプ設定、削除時の移管先、他プラグインによって扱いが異なります。本人のコメントはユーザー削除だけで全消去されるとは限りません。所有投稿を削除した場合、その投稿のコメントも影響します。UsersWP独自データやマルチサイトの削除挙動は別途調査が必要です。

ローカル検証：`php tests/user-withdrawal-check-test.php`。実DB・実WordPress・実ブラウザでの確認は別途行ってください。

## 退会処理基盤：保存直前の状態確認

退会は管理者が手動で進めます。将来、同じ画面で本人確認 → Square契約終了・課金停止・利用期間の確認 → 退会前チェック → 開始／書込み停止 → ウォッチ削除 → AI個人履歴削除 → WordPressユーザー削除 → 残存確認／完了記録を、一段階ずつ操作する予定です。今回、開始・清掃・削除・完了ボタンや画面統合は追加していません。Square自動解約・Free自動変更も行いません。

### データ保存と状態

`{prefix}egov_user_withdrawals`は維持します。InnoDB、`process_uuid CHAR(36)`主キー、`user_id BIGINT UNSIGNED` UNIQUE、`phase VARCHAR(20)`、`revision BIGINT UNSIGNED DEFAULT 1`、`claim_token CHAR(32) NULL`、`claimed_at DATETIME NULL`、`started_audit_id / last_audit_id BIGINT UNSIGNED NULL`、`created_at / updated_at DATETIME NOT NULL`、`completed_at DATETIME NULL`です。日時はUTC。氏名・メール・Square情報・同意記録は重複保存しません。

レコードなしを未開始、`started / cleaned / deleting`を処理中、`completed`を完了と扱います。未知の状態や不正な記録は未開始とみなさず保存を拒否します。以前の保存予約状態が万一DBに残っている場合も、自動的に削除・完了扱い・許可には変換しません。

有効化・管理画面の更新検出でテーブルを初期化し、検証後にスキーマバージョン1を保存します。既存の不適合テーブルを自動修復せず、通常表示ごとのDDLも実行しません。カラム・テーブルの追加変更はありません。反映前にバックアップし、管理画面で初期化を確認してください。

### 通常保存への影響

保存予約、通常保存用の所有者トークン、入れ子予約、通常保存用の独立接続、SAVEPOINTによるトランザクション検査は撤去しました。通常保存のためのINSERT・DELETE・BEGIN・COMMIT・ROLLBACKは追加しません。保存失敗後も予約等のレコードは残しません。

ウォッチ、通知設定、AI個人履歴、Free利用回数、Standard同意は、従来の`$wpdb`と`update_user_meta()`で保存します。metadataフック・キャッシュ処理はWordPress標準APIに任せます。保存直前に共有接続で退会状態を読み、開始済み・完了済み・取得失敗なら拒否します。スキーマ検証のみリクエスト内で再利用し、ユーザーの退会状態はキャッシュしません。

外部AI生成・法令検索の後にも、実際の保存直前に状態を確認します。ウォッチ上限調整は各UPDATE前にも確認し、途中で退会開始が観測された場合は以降の更新を停止します。ウォッチ登録・再開の件数はSQLエラー・NULL・不正な数値を検証し、取得失敗を0件として扱いません。

### 許容する競合と運用

状態確認と保存は一つのトランザクションではありません。確認を通過した後で退会が開始され、その保存が後から完了する競合を残余リスクとして許容します。通常保存の同時実行やFree回数更新の厳密な排他も保証しません。共有接続の既存トランザクションやレプリカが古い状態を読む場合の反映遅延も、実環境で確認が必要です。削除後に残存するウォッチ・個人履歴等を管理者が確認し、元の処理が続いている可能性があれば再確認する運用が必要です。一度の確認で将来の遅延書込みまで排除できるとは扱いません。今回、残存確認・清掃の実行機能自体は未実装です。

Free履歴と利用回数の部分成功リスクも維持します。履歴だけ保存されて回数更新が失敗すると、再表示は既存履歴として扱われ、回数の自動補正は行いません。回復用user_metaや履歴件数からの再計算は追加しません。Free累計3回・Standard暦月100回・共有AIキャッシュの仕様は変更しません。

### Square管理の操作別制御

既存の独立mysqli接続、トランザクション、ユーザー行ロック、nonce・権限・署名・監査・結果不明時の処理は維持します。既存の解約メール送信予約は通常保存の予約とは別の機能なので維持します。同じ接続・トランザクション内で退会状態を読みます。

- 契約登録・請求書からのStandard承認・利用者の新規解約申請等は、開始済みの場合に拒否します。
- 管理者の既存Free変更と利用終了日の登録・訂正は、退会を終えるための操作として処理中も利用可能です。サーバー内の操作区分のみで許可し、権限・nonce・署名・理由・契約整合性の検証は省略しません。
- 完了済み、不正状態、読み取り失敗では上記の例外操作も拒否します。
- Free変更と同時の解約完了記録は既存トランザクションで保存します。その後の通常ウォッチ自動調整は停止され、既存の警告になる場合があります。
- 退会中の通常の解約メール予約・結果保存も停止対象です。必要な利用終了日通知等は退会開始前に行う運用を基本としてください。

### 保護対象と今後の段階管理

「設定 → e-Gov Law Monitor AI」でサービス用IDを指定します。Subscriberのみ対象とし、他ロール併有、管理・投稿・内部API権限、`law_watch_api`、指定ID、マルチサイトは対象外です。アカウント自体の判定を標準削除と共通化し、管理者本人の除外は別に行います。Application Passwordだけで永久に除外しません。

claim_token等と退会側の内部ロック関数は将来の段階実行管理用に保持しますが、通常保存では使用しません。現行の`cleaned`は清掃完了をまとめた状態なので、ウォッチとAI履歴を別ボタンにする時点でphase許可値・遷移・各操作の監査・失敗後の再開条件を設計する必要があります。VARCHARの状態値と既存監査IDで対応できる範囲はありますが、処理開始や段階実行を先行実装していません。

標準削除の権限フィルターは維持します。直接`wp_delete_user()`を呼ぶプラグイン・WP-CLI・直接SQLや、本プラグインの状態確認を通らない外部書込みまでは防げません。

### テストと実環境確認

`withdrawal-foundation-test.php`は実際の保存関数と状態確認を通し、WordPress／DBの境界だけを代替します。通常保存で退会テーブルへ書き込まないこと、状態・読み取り失敗による拒否、ウォッチ件数異常、許容する確認後の競合を確認します。保存予約用の接続・テストは削除しました。

実WordPressのmetadataフック・キャッシュ・UsersWP、実MySQLの読み取り／同時実行、削除後の遅延書込み・残存確認はステージングで検証が必要です。本番DB・Squareへの実通信テストは行っていません。
